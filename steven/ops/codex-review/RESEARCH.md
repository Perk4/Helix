# Supported Codex review automation for Azure DevOps pull requests

_Research checked 2026-09-22. Sources are limited to OpenAI and Microsoft primary documentation._

## Conclusion

Azure DevOps (ADO) has no OpenAI-provided Codex action comparable to the official GitHub Action. The supported composition is therefore:

1. Use an **Azure Repos Build validation branch policy** to start an Azure Pipeline when a PR is opened or its source changes. Azure Repos does not support YAML `pr:` triggers; it implements PR validation with branch policies. Validation builds run against the PR's synthetic merge commit. [Microsoft: Build Azure Repos Git repositories](https://learn.microsoft.com/en-us/azure/devops/pipelines/repos/azure-repos-git?view=azure-devops) [Microsoft: Branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies?view=azure-devops)
2. In the job, obtain the canonical PR and commit identities from ADO, create a diff, and invoke the Codex CLI noninteractively with `codex exec`. OpenAI documents `codex exec` as the CI/script interface, read-only sandboxing as its default, `--output-schema` for structured output, and `--output-last-message` for capturing the final response. [OpenAI: Non-interactive mode](https://developers.openai.com/codex/non-interactive/)
3. Use the ADO Pull Request Threads REST API for a summary thread and file/line threads, and optionally the Pull Request Statuses API for a stable `genre/name` state shown in the PR. [Microsoft: Create PR thread](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-threads/create?view=azure-devops-rest-7.1) [Microsoft: Create PR status](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-statuses/create?view=azure-devops-rest-7.1)

This repository already keeps the automation under `ops/codex-review/` and uses a server-controlled Classic definition with inline tasks. That is a defensible trust boundary: an Azure Repos PR build evaluates merged PR content, so putting the reviewer orchestration in the reviewed repository's YAML would let the PR alter the job that receives credentials. Microsoft confirms that the merged YAML governs Azure Repos PR behavior. [Microsoft: Build Azure Repos Git repositories](https://learn.microsoft.com/en-us/azure/devops/pipelines/repos/azure-repos-git?view=azure-devops)

## Exact ADO permissions and scopes

ADO **security permissions** and OAuth/PAT **scopes** are separate controls. A job's `System.AccessToken` is a short-lived job token; its effective access comes from the job authorization scope and the corresponding project- or collection-build-service identity's permissions. It is not a PAT for which the pipeline selects `vso.*` scopes. Microsoft recommends project-scoped job authorization because collection scope can expose every repository in the organization. [Microsoft: Job access tokens](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/access-tokens?view=azure-devops)

The following is the least-privilege matrix for a same-project, same-repository reviewer.

| Capability | ADO identity permission | OAuth/PAT scope when an external credential calls the REST endpoint | Notes |
|---|---|---|---|
| Create the review pipeline | Installer: **Create build pipeline**; to change it later, **Delete or edit build pipeline** | `vso.build_execute` for Build Definitions create/update | Build permissions are documented in the pipeline permission table; the REST create endpoint declares `vso.build_execute`. [Microsoft: Pipeline permissions](https://learn.microsoft.com/en-us/azure/devops/pipelines/policies/permissions?view=azure-devops) [Microsoft: Create build definition](https://learn.microsoft.com/en-us/rest/api/azure/devops/build/definitions/create?view=azure-devops-rest-7.1) |
| Make PRs trigger it | Installer: **Edit policies** on the target branch/repository, or Project Administrators membership | `vso.code_write` for Policy Configurations create/update | Configure an automatic Build validation policy (`manualQueueOnly=false`) on each target branch. There is no extra scope used by the runtime job merely because ADO queued it. **Queue builds** is needed by identities that manually queue builds. [Microsoft: Branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies?view=azure-devops) [Microsoft: Create policy configuration](https://learn.microsoft.com/en-us/rest/api/azure/devops/policy/configurations/create?view=azure-devops-rest-7.1) |
| Checkout/fetch PR source and target in the same repository | Runtime build-service identity: repository **Read** | `vso.code` | Use a project-scoped job token and grant Read only on the reviewed repository. [Microsoft: Azure Repos checkout/security](https://learn.microsoft.com/en-us/azure/devops/pipelines/repos/azure-repos-git?view=azure-devops) [Microsoft: Checkout schema](https://learn.microsoft.com/en-us/azure/devops/pipelines/yaml-schema/steps-checkout?view=azure-pipelines) |

| Post/update summary or inline threads/comments | Runtime build-service identity: repository **Contribute to pull requests** (and Read) | `vso.threads_full` **or** `vso.code_write` | `vso.threads_full` is narrower: read/write PR comment threads. Create and update endpoints accept it. The repository permission reference describes Read/PR contribution behavior. [Microsoft: Create PR thread](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-threads/create?view=azure-devops-rest-7.1) [Microsoft: Update PR comment](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-thread-comments/update?view=azure-devops-rest-7.1) [Microsoft: Git repository permissions](https://learn.microsoft.com/en-us/azure/devops/repos/git/set-git-repository-permissions?view=azure-devops) |
| Post PR status | Runtime build-service identity: repository **Contribute to pull requests** (and Read) | `vso.code_status` **or** `vso.code_write` | Microsoft explicitly requires Contribute to pull requests for a service posting status. `vso.code_status` is the narrower REST scope. A status is informational unless a matching Status check branch policy is configured. For a repository in another project, also grant the pipeline project access to that project and grant its build-service identity Read on the repository. Do not solve this by switching to a collection-scoped token. For YAML pipelines with **Protect access to repositories** enabled, explicitly reference the repository in a `checkout` step. [Microsoft: Secure repository access](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/secure-access-to-repos?view=azure-devops)

### Minimum runtime grant

For this use case, the project build-service identity should have only:

- **Read** on the reviewed repository;
- **Contribute to pull requests** on that repository (for threads and status);
- no Contribute/push, branch creation, policy editing, bypass, force-push, or repository administration permissions.

Expose `System.AccessToken` only to the admission/publishing steps that call ADO. In YAML it must be explicitly mapped into a step; in Classic, **Allow scripts to access the OAuth token** enables script access. [Microsoft: Predefined variables (`System.AccessToken`)](https://learn.microsoft.com/en-us/azure/devops/pipelines/build/variables?view=azure-devops)

## Correct diff and comment flow

1. Require `Build.Reason == PullRequest`; obtain the repository and PR IDs from predefined variables, but call `GET .../pullRequests/{id}` and verify repository, target ref, active/non-draft state, and current commits before spending money or publishing. PR variables are initialized for branch-policy PR builds. [Microsoft: Predefined variables](https://learn.microsoft.com/en-us/azure/devops/pipelines/build/variables?view=azure-devops)
2. Compare `Build.SourceVersion` with `lastMergeCommit` to reject a stale run. Use `lastMergeSourceCommit` and `lastMergeTargetCommit` as immutable endpoints. ADO documents all three fields on the PR response. [Microsoft: Get PR](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/get-pull-request?view=azure-devops-rest-7.1)
3. Either compute `git merge-base <target> <source>` and `git diff <base> <source>` after a full fetch, or call `diffs/commits` with commit versions and `diffCommonCommit=true`. The REST endpoint finds the common commit and declares `vso.code`. [Microsoft: Get commit diff](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/diffs/get?view=azure-devops-rest-7.1)
4. Ask Codex for schema-constrained JSON containing a summary and findings. Validate it locally, including path and line bounds, before publishing. [OpenAI: Non-interactive mode](https://developers.openai.com/codex/non-interactive/)
5. Post the summary by creating a thread without file context. For an inline finding, create a thread with `threadContext.filePath` and right-side start/end positions. For PRs with iteration support, also include `pullRequestThreadContext.changeTrackingId` and `iterationContext`; obtain the tracking ID from the iteration changes endpoint. [Microsoft: Create PR thread](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-threads/create?view=azure-devops-rest-7.1) [Microsoft: Get PR iteration changes](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-iteration-changes/get?view=azure-devops-rest-7.1)
6. Immediately before publication, refetch the PR and discard output if source, target/merge, target branch, active state, or draft state changed. Associate statuses with the current iteration when possible. Use a deterministic hidden marker or stored thread IDs so retries update an existing bot-authored review.

## Codex authentication in unattended CI

OpenAI says API-key authentication is the default choice for programmatic Codex CLI workflows such as CI/CD. For one invocation, pass `CODEX_API_KEY` in that process's environment; `codex exec` also reuses saved CLI authentication, but cached credentials can live in plaintext `~/.codex/auth.json`, so a pre-logged-in shared runner is not the secure default. [OpenAI: Authentication](https://developers.openai.com/codex/auth/) [OpenAI: Non-interactive mode](https://developers.openai.com/codex/non-interactive/)

For ChatGPT Enterprise, Codex access tokens are an advanced alternative for trusted private runners when workspace-managed entitlement and controls are specifically required. OpenAI still calls API keys the right default for automation. [OpenAI: Authentication](https://developers.openai.com/codex/auth/)

### Recommended secure implementation

- Store a **dedicated OpenAI project/service-account API key** as an ADO secret, with separate spend/rate limits and rotation from other workloads. Never place it in the repository, prompt, command line, logs, artifact, or persistent Codex home.
- Do **not** set `OPENAI_API_KEY` or `CODEX_API_KEY` at job scope. OpenAI warns that repository build scripts, lifecycle hooks, or compromised tasks in the same job can read job-level secrets. Map `CODEX_API_KEY` only to the single `codex exec` process. [OpenAI: Non-interactive mode](https://developers.openai.com/codex/non-interactive/)
- Do not execute PR-controlled code before or during the secret-bearing invocation. Generate a patch using trusted, server-controlled code, place only that review input in a fresh temporary directory, and invoke Codex there. Install a pinned Codex CLI version outside the checkout and disable package lifecycle scripts.
- Run `codex exec --ephemeral --sandbox read-only` with approvals disabled for unattended operation, no MCP servers, no web search, and no unnecessary environment inheritance. OpenAI recommends the least-capable sandbox; `--ephemeral` avoids persisting session rollouts. [OpenAI: Non-interactive mode](https://developers.openai.com/codex/non-interactive/) [OpenAI: Agent approvals and security](https://developers.openai.com/codex/agent-approvals-security/)
- Keep ADO and OpenAI credentials separated by process: admission/publisher receives only `System.AccessToken`; Codex receives only `CODEX_API_KEY`; neither receives both. Remove checkout Git auth headers/credential helpers before invoking Codex and leave `persistCredentials` false.
- Treat the diff, PR text, comments, and commit messages as hostile prompt input. Give Codex no write capability and no external tools; validate output and perform ADO writes in a small deterministic publisher after rechecking the PR revision.
- Prefer a Microsoft-hosted disposable agent or a dedicated ephemeral self-hosted runner. Do not seed reusable `auth.json` into a general-purpose runner.

This architecture leaves one unavoidable boundary: the Codex process and its installed package receive the OpenAI key in memory. Pin and review the package version, monitor usage, rotate on suspicion, and keep the key incapable of accessing anything except the intended OpenAI project.

## Permissions for PR creation, labels, work-item links, and work-item updates

Azure DevOps evaluates two independent gates: the identity's Azure DevOps security permissions/access level, and the PAT/OAuth token's scopes. A broad token scope does not grant an identity a denied Azure DevOps permission. For a pipeline `System.AccessToken`, grant the listed permissions to the job's build-service identity; unlike a PAT, that job token does not have a user-selected `vso.*` scope list. [Microsoft: Job access tokens](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/access-tokens?view=azure-devops)

| Operation | Azure DevOps access and security permissions | PAT/OAuth scope | Exact conclusion |
|---|---|---|---|
| Create a pull request from an existing source branch | At least **Basic** access, repository **Read**, and **Contribute to pull requests**. Microsoft defines the latter as permission to “create, comment on, and vote on pull requests”; its task-level prerequisite also describes **Contributors or corresponding permissions** for creating/completing PRs. | `vso.code_write` | No push, policy-bypass, or repository-administration permission is required merely to create the PR. [Microsoft: permission reference](https://learn.microsoft.com/en-us/azure/devops/organizations/security/permissions?view=azure-devops) [Microsoft: create a PR prerequisites](https://learn.microsoft.com/en-us/azure/devops/repos/git/pull-requests?view=azure-devops) [Microsoft: PR Create REST API](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/create?view=azure-devops-rest-7.1) |
| Add or remove an Azure Repos PR label | Repository **Read** and **Contribute to pull requests**. Microsoft does not document a separate UI security bit for PR labels; labels are a PR-management operation, so use the PR-contribution permission rather than source-code **Contribute**. | `vso.code_write` for both create and delete | PR labels are not Azure Boards work-item tags and do not require **Create tag definition**. [Microsoft: PR label Create](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-labels/create?view=azure-devops-rest-7.1) [Microsoft: PR label Delete](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-labels/delete?view=azure-devops-rest-7.1) [Microsoft: permission reference](https://learn.microsoft.com/en-us/azure/devops/organizations/security/permissions?view=azure-devops) |
| Link a PR to a work item | Repository **Read** plus area-path **View work items in this node** and **Edit work items in this node** for the work item. | `vso.work_write` when adding/removing the PR `ArtifactLink` by PATCHing the work item's `relations`; `vso.code` is sufficient only to list a PR's already-linked work items. | Treat linking as a work-item edit, not as a label/tag permission. The current Git API documents only listing PR work items; the documented generic write mechanism is Work Items Update, which can add/remove relations. [Microsoft: development links and prerequisites](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/connect-work-items-to-git-dev-ops?view=azure-devops) [Microsoft: Work Items Update](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1) [Microsoft: list PR work items](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-work-items/list?view=azure-devops-rest-7.1) |
| Change a work item's state or assign/remove existing work-item tags | At least **Basic** access plus area-path **View work items in this node** and **Edit work items in this node**. Normal updates remain subject to process/workflow rules. | `vso.work_write` | PATCH `/fields/System.State` or `/fields/System.Tags`. Do not grant rule-bypass permissions for ordinary automation. [Microsoft: work-tracking permissions](https://learn.microsoft.com/en-us/azure/devops/organizations/security/set-permissions-access-work-tracking?view=azure-devops) [Microsoft: Work Items Update, including tag examples](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1) |
| Introduce a previously nonexistent work-item tag and assign it | All permissions in the preceding row, plus project-level **Create tag definition** set to **Allow**. | `vso.work_write`; there is no additional PAT/OAuth “tag-definition” scope | Microsoft explicitly says denying **Create tag definition** prevents creating definitions but does not prevent assigning existing tags to editable work items. Adding the new value through `System.Tags` creates/uses the project-shared definition. [Microsoft: set work-item tag permissions](https://learn.microsoft.com/en-us/azure/devops/organizations/security/set-permissions-access-work-tracking?view=azure-devops#tags) [Microsoft: add tags prerequisites](https://learn.microsoft.com/en-us/azure/devops/boards/queries/add-tags-to-work-items?view=azure-devops) [Microsoft: Work Items Update](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/update?view=azure-devops-rest-7.1) |
| Create a source branch and push commits | Repository **Read** and **Create branch** to publish a new branch. **Contribute** is required to push to an existing branch; Azure DevOps notes that a user with **Create branch** can push the new branch even without repository-level **Contribute**, and the branch creator receives branch-level **Contribute**. | `vso.code_write` | Grant **Contribute** only on the automation's source-branch namespace/branch where practical. Normal creation/push needs neither **Force push** nor either policy-bypass permission. Branch policies still apply. [Microsoft: Git permission definitions](https://learn.microsoft.com/en-us/azure/devops/organizations/security/permissions?view=azure-devops) [Microsoft: Pushes Create REST API](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pushes/create?view=azure-devops-rest-7.1) |

### Least-privilege grant for this automation

If branches already exist, grant the automation identity **Basic** access, repository **Read** and **Contribute to pull requests**, area-path **View work items in this node** and **Edit work items in this node**, and project **Create tag definition** only if it must invent new work-item tags. For a PAT/OAuth credential that performs every listed write, request `vso.code_write` plus `vso.work_write`. If it also creates/pushes source branches, add repository **Create branch** and branch-scoped **Contribute**; the token scope remains `vso.code_write`. Do not grant **Force push**, policy bypass, **Manage permissions**, or **Edit policies** for these operations.
